Sol Verifies the Wrong Thing

The model often runs real checks. The problem is that those checks inherit its first interpretation of the task.

By Auriel · September 8, 2026 · 5 minute read

I have been keeping up with the latest model releases. Sol is making real progress against Opus 5. Terra also clears Sonnet 5 by 6.2 points on Terminal-Bench 3.0. That is good. The gap I would attack next is still very practical: independent verification and instruction following.[1]

In my own repos, I see the same failure mode repeatedly with subagents. I give one a scoped task and an existing unit test. It skips the test, writes its own sort of vibe test, gets that to pass, and says the work is done.

So the issue is not always that the model refuses to test. It tests its interpretation of the task. It does not establish that the core requirement is true.

The sad path I keep seeing A proxy passes. The task still fails.
  1. 01Read the taskA real requirement is present.
  2. 02Choose one readingThe first plausible interpretation becomes the plan.
  3. 03Build to that readingThe implementation can be competent.
  4. 04Write a proxy testThe check inherits the same interpretation.
  5. 05Watch it passLocal evidence confirms the local story.
  6. 06Claim completionThe actual acceptance test was never run.
Hidden verifier checks the stated requirement.FAIL

The public trajectories show the same thing

Turing ran Sol with Codex for 800 trials on its Terminal-Bench 3.0 task set. It classified 338 agent-attributable failures. Of those failures, 238 ended with a confident completion claim after the model's own checks appeared to pass. That is 70.4%. Another 47, or 13.9%, shipped without exercising the deliverable.[2]

Instruction following shows up in the same data. 102 failures, or 30.2%, under-modeled a stated requirement. Another 77, or 22.8%, missed a numeric or perceptual bar. These are not abstract reasoning misses. They are cases where the task named something and the final verification never established it.[2]

Example 1

SVG winding correction

What Sol checked
Valid XML, preserved control points, and representative fill behavior.
What Sol did not check
It never ran a renderer against the required pixel-difference bar.
Outcome
The hidden renderer failed the self-intersecting SVG. Sol had already claimed correct rendering.
Example 2

Partition rate limiter

What Sol checked
Partition safety, reconciliation, and isolated resets.
What Sol did not check
Whether the limiter actually used the available quota.
Outcome
FAIL: window underutilized: 0 < N
Example 3

Consent cache drift

What Sol checked
Sequential cases, 600 randomized events, and a concurrency retry test.
What Sol did not check
A required source of consent state was absent from its system model.
Outcome
Unsubscribed users still received the campaign.

More test volume did not save these runs. The consent agent ran 600 randomized events. The rate limiter passed its simulator. The SVG agent inspected multiple proxies. The coverage was wrong, so every extra check reinforced the same mistaken task representation.[2]

My read: the solution policy and the verification policy are too coupled. One interpretation generates the implementation, the checks, and the final confidence claim.

The path I want instead

A happier verification trajectory The check gets an independent chance to disagree.
  1. 01List requirementsKeep every constraint visible through the run.
  2. 02Name the evidenceMap each requirement to an observable check.
  3. 03BuildImplement without redefining the target.
  4. 04Run the real verifierUse the repository test or task-native metric.
  5. 05Try to falsifyFresh context searches for missing constraints and counterexamples.
  6. 06Calibrate the claimClaim only what the evidence established.
If a check fails, fix the artifact and rerun the whole acceptance path.PASS WITH RECEIPTS

What I would train next

  1. Independent falsification.Let a fresh verifier read the task and artifact without inheriting the builder's rationale. Reward it for finding a counterexample, not for agreeing.
  2. Requirement-to-test coverage.Make the model keep a durable requirement ledger. Every requirement needs a named test and a result before completion.
  3. Task-native evidence.Reward the repository test, renderer, benchmark metric, or end-to-end behavior. Give less credit to proxy checks when the real criterion is available.
  4. Calibrated stopping.Reward “not yet verified” when a critical property was not exercised. A truthful incomplete status is better than a polished false completion.
  5. In-harness co-training.Train the model and scaffold around the actual failure loop. Keep instruction following as a regression metric, especially under subagent delegation and context compaction.
Important caveat The public leaderboard is a model-plus-harness comparison. Opus 5 at max with mini-SWE-agent scores 42.7%, while Sol at max with Codex scores 34.6%. That 8.1 point gap does not isolate model weights. Before changing training, I would run a matched model by harness factorial and break failures out by interpretation, implementation, verification, and stopping.[1]

TL;DR: Sol is close enough to be interesting. The next hill climb is not “make it check more.” It is “make verification independent enough to prove the model's first interpretation wrong.” That feels trainable, measurable, and product-relevant. It is also exactly the kind of work I would be excited to help with. Hopefully you guys agree ~~ :)
